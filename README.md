# Game Digital Wallet (GDW) — game-engine frameworks

A small, dependency-free **prototype** that adapts the EUDI Wallet Architecture
and Reference Framework's selective-disclosure credential model (SD-JWT VC,
ARF §5.4.3) to the needs of game developers. It ships the same token format and
the same behaviour in six languages so a game client, a game server, and a
backend can all speak it:

| Language | Engine / runtime | Folder | Tests |
| --- | --- | --- | --- |
| C++17 | Unreal Engine, any C++ game server | [`cpp/`](cpp/) | `61/61` |
| C# (.NET 10) | Unity, Godot (.NET), backend | [`csharp/`](csharp/) | `61/61` |
| GDScript | Godot 4.x (no native deps) | [`gdscript/`](gdscript/) | `55/55` |
| Rust | Bevy, Rust game servers, `wasm32` | [`rust/`](rust/) | `58/58` (`61/61` with ES256) |
| Python | Panda3D, PyGame, Ursina, servers | [`python/`](python/) | `58/58` (`61/61` with ES256) |
| Lua | Defold, LÖVE (LuaJIT), Lua 5.1+ | [`lua/`](lua/) | `55/55` |

Every implementation replays the *same* cross-language test vectors
([`test-vectors/vectors.json`](test-vectors/vectors.json)), generated by
[`test-vectors/generate_vectors.py`](test-vectors/generate_vectors.py) — the
executable form of the specification. If all of them pass, the formats are
byte-for-byte identical.

> **This is not an official EU specification** and is **not interoperable with
> production EUDI Wallets.** It is a teaching / prototyping aid. The default
> algorithm is **HS256 (symmetric HMAC)**, which is only safe when issuer and
> verifier are the same trusted backend. See [SPEC.md](SPEC.md) before shipping.

---

## What it is for

A player's credential ("over 18", "owns Season Pass", "member of guild X") is
signed once by an issuer. Later, a game server asks for *only* the attribute it
needs, and the wallet reveals only that — plus a key-binding proof that the
answer is fresh and came from this device. This maps directly onto game
problems:

* **Age gating & matchmaking** — prove "over 18" without revealing a birth date.
* **Portable entitlements** — a season pass that works across your titles and
  platforms without a central account call on every launch.
* **Guild membership & rank** — verifiable membership a third-party tournament
  server can trust.
* **Tournament passes** — time-boxed, non-transferable entry proofs.
* **Verified accounts** — prove control of a platform identity.
* **Parental consent** — prove a guardian consent claim is present and valid.

## ARF mapping (at a glance)

| GDW term | Game meaning | ARF counterpart |
| --- | --- | --- |
| Wallet | Player-side credential store | Wallet Unit |
| Credential | Signed bundle of claims | Attestation / EAA (SD-JWT VC) |
| Issuer | Platform holder / studio backend | PID / Attestation Provider |
| Verifier | Matchmaker / game server | Relying Party |
| Request | What is asked for and why | Presentation request (OpenID4VP-style) |
| Presentation | JWT + selected disclosures + key binding | Presentation (VP) |
| Trust store | Issuers a verifier believes | Trusted List / LoTE |

```
frameworks/
  SPEC.md                     the normative GDW token specification
  test-vectors/
    generate_vectors.py       executable spec / vector generator
    vectors.json              shared vectors every framework must pass
  cpp/                        header-only C++17 (OpenSSL optional, for ES256)
  csharp/                     .NET library + example + console test runner
  gdscript/                   Godot 4 addon + example + headless test runner
  rust/                       crate for Bevy / servers (ES256 via optional feature)
  python/                     package for Panda3D / PyGame / servers (ES256 via `cryptography`)
  lua/                        modules for Defold / LÖVE / Lua 5.1+ (HS256 only)
```

## Running the tests

**C++** (needs a C++17 compiler; OpenSSL optional but enables the ES256 round-trip):

```bash
cd cpp
cmake -S . -B build && cmake --build build
cd build && ctest --output-on-failure      # or: ./wallet_tests ../test-vectors/vectors.json
```

**C#** (needs the .NET SDK):

```bash
cd csharp
dotnet run -c Release --project Tests/EudiGameWallet.Tests -- ../test-vectors/vectors.json
```

**GDScript** (needs Godot 4.x on `PATH`, or use an absolute path to the binary):

```bash
cd gdscript
godot --headless --path . --import                     # first time only
godot --headless --path . --script res://tests/run_tests.gd
```

**Rust** (needs a Rust toolchain; the core is dependency-free, `es256` is optional):

```bash
cd rust
cargo test                                            # 58/58
cargo test --features es256                           # 61/61 (adds P-256 round trip)
```

**Python** (stdlib only; ES256 activates when `cryptography` is installed):

```bash
cd python
python3 tests/run_tests.py                            # 58/58 (61/61 with `cryptography`)
python3 tests/test_units.py
```

**Lua** (any of `lua` / `luajit` / `lua5.1`; pure Lua, no C dependencies):

```bash
cd lua
lua tests/run_tests.lua                               # 55/55 (HS256 only)
luajit tests/run_tests.lua
lua5.1 tests/run_tests.lua
lua tests/test_units.lua
```

## Running the end-to-end example (all six print identical numbers)

```bash
cd cpp      && cmake -S . -B build && cmake --build build && ./build/basic_flow
cd csharp   && dotnet run -c Release --project Examples/BasicFlow
cd gdscript && godot --headless --path . --script res://examples/basic_flow.gd
cd rust     && cargo run --example basic_flow
cd python   && python3 examples/basic_flow.py
cd lua      && lua examples/basic_flow.lua
```

## Device camera support (why Roblox is the odd one out)

The GDW flow needs the *device* camera only for capturing a credential QR code
or a proof-of-presence image — never for rendering a scene. That matters when
choosing an engine, because in-game 3D cameras are universal but *device camera*
access is not:

| Engine | Device camera (photo/video) | How |
| --- | --- | --- |
| Unity | ✅ Full | `WebCamTexture`, plus AR Foundation `XRCameraSubsystem`; Android/iOS/WebGL with runtime permission APIs. |
| Unreal Engine | ⚠️ Limited | Desktop webcam via Media Framework (`EnumerateWebcamCaptureDevices`); reliable mobile capture needs a plugin (e.g. DirectCamera). |
| Godot 4 | ✅ Full | `CameraServer` / `CameraFeed`; implemented on Linux, macOS, Android, iOS (iOS export needs `modules/camera`). |
| Godot (.NET) | ✅ Full | Same engine core — the C# bindings expose the identical `CameraServer` / `CameraFeed`. |
| Defold | ✅ Full | Official [`extension-camera`](https://defold.com/extension-camera/) native extension; macOS, iOS, Android (`camera.start_capture` / `camera.get_frame`). |
| LÖVE (love2d) | ❌ Restricted | No built-in camera (only `love.audio` mic recording); capture needs a custom C/C++ module (ESCAPI/OpenCV), effectively desktop-only. |
| Bevy / Amethyst | ⚠️ Limited | No built-in support; via the `nokhwa` crate (`bevy_webcam` / `bevy_nokhwa`) on native, or `getUserMedia` on `wasm32`. Amethyst is unmaintained. |
| Cocos2d-x | ⚠️ Limited | No cross-platform camera API; uses a native `ImagePicker`/`Intent` on Android and a UIKit picker on iOS, with custom JSB binding. |
| Construct 3 | ✅ Full | Built-in **User Media** object (camera + mic, snapshot to Sprite/Tiled Background) on top of `getUserMedia`. |
| GDevelop | ✅ Full | Web/`getUserMedia` based; camera used by face-capture / tracking extensions. |
| PlayCanvas / Babylon.js / Three.js | ✅ Full | Web engines: `navigator.mediaDevices.getUserMedia` → a video texture (`Babylon.VideoTexture.CreateFromWebCam`, PlayCanvas video-texture tutorial, Three.js `VideoTexture`). |
| Roblox (Luau) | ❌ Restricted | No general device-camera API for game code. `PlayerViewService:GetDeviceCameraCFrame` is **mobile-only** and only when the user opts in; webcam use is limited to avatar facial animation. Not usable for QR scanning. |

**Consequence:** the credentials themselves are engine-agnostic (the same
`test-vectors/vectors.json` vectors replay in C++, C# and GDScript), so a game
server or backend can verify a presentation from *any* platform. Only the
*capture* step — scanning a QR code — is camera-bound. On Roblox the capture
half is unsupported today; a Roblox integration would have to receive an
already-captured presentation (e.g. over `HttpService`) rather than scan it
in-engine. See [`SPEC.md`](SPEC.md) for the wire format that makes this split
possible.
